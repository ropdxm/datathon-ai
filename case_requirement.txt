
Техническое задание Datathon 26
AI-сервис для выявления нарушений кассовой дисциплины по видеозаписям
1. Контекст и бизнес-задача
Банковские кассовые операции сопровождаются процедурами безопасности и контроля. Часть потенциальных нарушений можно определить визуально по видеозаписи, однако ручной просмотр видео требует времени.
ForteBank предлагает участникам разработать готовый AI-сервис, который анализирует видеозаписи работы кассира, выявляет визуально наблюдаемые признаки возможного нарушения и показывает проверяющему конкретный фрагмент, время события и обоснование результата.
2. Задача участников
Разработать и развернуть работающий сервис с пользовательским интерфейсом, в который представитель заказчика может загрузить новую видеозапись для проверки. После обработки сервис должен сообщить, обнаружены ли признаки нарушения и, если да, представить кадр-доказательство, таймкод и ссылку на соответствующее правило или нормативный источник.
Команда самостоятельно исследует доступные открытые нормативные источники, определяет релевантные правила, формирует подход к классификации событий и выбирает технический подход. Решение должно работать полностью локально, без обращения к облачным AI-сервисам (см. раздел 7).
3. Исходные данные
Вместе с кейсом командам передаётся обучающий датасет из коротких видеороликов, демонстрирующих корректные действия и ситуации с возможными нарушениями.
Полный внутренний регламент кассира, исчерпывающий список ожидаемых нарушений и нормативные источники заказчиком не предоставляются. Команда самостоятельно исследует предметную область и обосновывает, какие правила возможно проверять по видео (см. раздел 6).
4. Обязательный пользовательский сценарий
Пользователь открывает веб-интерфейс и загружает видеофайл.
Сервис запускает анализ и отображает статус обработки.
По завершении сервис показывает один из результатов: «Нарушение не обнаружено», «Обнаружены признаки возможных нарушений».
Для каждого обнаруженного возможного нарушения (в одном видео их может быть несколько) сервис указывает его тип, таймкод и описание.
Сервис показывает один или несколько кадров-доказательств из соответствующего фрагмента.
Сервис кратко описывает, что именно видно на видео и почему это может указывать на нарушение.
Сервис указывает правило и нормативный источник: название документа, пункт/раздел. 
Кроме интерфейса, обязательно сервис должен быть доступен через API (раздел 10): по нему жюри проверяет решения на тестовых видео.
5. Обязательные требования к результату
Работающий сервис — фронтенд и серверная часть; пользователь загружает видео и получает результат без ручного запуска кода.
Обнаружение событий — анализ визуально наблюдаемых действий, которые могут свидетельствовать о нарушении.
Вердикт — один из двух результатов (см. раздел 4, п. 3). 
Таймкод — временная отметка для каждого события.
Кадр-доказательство — конкретный кадр или набор кадров, позволяющий человеку проверить вывод.
Обоснование — краткое и понятное проверяющему описание наблюдаемого действия без неподтверждённых предположений.
6. Самостоятельное исследование нормативной базы
Команда самостоятельно находит и изучает публичные источники — нормативные акты Республики Казахстан (НБРК, adilet.zan.kz), относящиеся к кассовым операциям, инкассации, организации и охране кассовых помещений и другим релевантным требованиям банковской сферы. В решении необходимо указать использованные источники и показать связь между источником, предполагаемым нарушением и наблюдаемым фрагментом видео.
7. Ограничения и допущения
Анализ выполняется на основании предоставленного видео и доступных команде открытых источников.
Доступ к производственным банковским системам, АБИС, внутренним журналам и инфраструктуре ForteBank не предоставляется.
Сервис не должен утверждать, что обнаружил нарушение, если для вывода необходимы невидимые на видео данные, например корректность проводки или системной сверки.
Результат является подсказкой для проверки человеком, а не окончательным юридическим или дисциплинарным заключением.
Локальность — решение работает полностью локально: все модели выполняются внутри развёрнутого командой сервиса. Обращение к облачным AI-сервисам и API (облачные LLM, мультимодальные модели, сервисы распознавания) при обработке видео запрещено, в том числе передача им видео, кадров или их описаний.
Переносимость — после загрузки весов сервис не должен требовать доступа в интернет для обработки видео, чтобы его можно было перенести во внутренний контур банка.
8. Что команда должна представить
Адрес работающего сервиса с пользовательским интерфейсом, адрес API (раздел 10) и API-ключ для жюри.
Инструкцию по запуску и использованию.
Краткое описание архитектуры, выбранного подхода и используемых моделей.
Описание найденных нормативных источников и принципа сопоставления правил с видео.
Перечень типов нарушений, которые распознаёт решение, с кратким описанием каждого.
Перечень ограничений решения и известных случаев ошибок.

10. API для проверки жюри
Помимо интерфейса для пользователей, сервис должен иметь публичный API. Через него жюри прогонит тестовые видео по всем решениям и соберёт результаты. По ним несколько команд будут приглашены на питчинг.
Доступ к API — по ключу. Команда сама создаёт ключ и передаёт его жюри вместе с адресом сервиса. Ключ передаётся в заголовке X-API-Key, запросы без верного ключа сервис отклоняет. Тестовые видео нельзя использовать для обучения, публиковать или передавать третьим лицам.
Обработка видео может занимать несколько минут, поэтому API работает в два шага:
Метод
Путь
Назначение
POST
/api/v1/analyze
Загрузить видео в формате .mov (поле file). В ответ возвращается job_id.
GET
/api/v1/jobs/{job_id}
Получить статус обработки (processing, done, failed) и результат.


Когда обработка завершена, результат возвращается в таком виде:
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Название типа нарушения",
      "timecode_sec": 44.2,
      "description": "Что видно на видео и почему это нарушение",
      "evidence_frames": [
        { "timestamp_sec": 44.2, "image_base64": "/9j/4AAQ..." }
      ]
    }
  ]
}
Поле
Описание
verdict
no_violation или violation — два результата из раздела 4, п. 3.
violations
Список нарушений; пустой, если нарушений нет.
type
Тип нарушения.
timecode_sec
Таймкод события в секундах от начала видео.
description
Что видно на видео и почему это может быть нарушением.
evidence_frames
1–3 кадра-доказательства в формате JPEG, закодированные в base64.


Если сервис недоступен или не вернул результат за 5 минут, видео засчитывается как необработанное.
Пример запроса:
curl -X POST https://team.example.kz/api/v1/analyze \
     -H "X-API-Key: <ключ>" -F "file=@video_017.mov"

Вопросы и ответы (FAQ)
A. Датасет
1. Сколько роликов в датасете и в каком они формате?
Минимум 40 роликов длительностью от 10 до 145 секунд. Формат — .mov (тестовые видео в том же формате), FPS — от 29, звука нет. Размер файла — около 29 МБ.
2. Есть ли разметка?
Для каждого видео указаны метка «нарушение» и таймкод, например: видео, 11-я секунда, нарушение. Тип нарушения не указывается — его команды определяют самостоятельно.
3. Какие это записи: постановочные или реальные? Какой ракурс?
Постановочные видео, ракурс сверху, одна камера, одна касса. В кадре кассир и другие люди — клиенты и инкассаторы.
4. Похожи ли тестовые видео на обучающие?
Да, видео будут похожими. Финальное видео для проверки будет снято под другим углом.
5. Как и когда выдаётся датасет?
По ссылке с момента старта; ссылка будет опубликована на сайте.
6. Можно ли загружать видео во внешние облачные сервисы, публиковать или хранить после хакатона?
Данные должны использоваться только в рамках хакатона.
7. Можно ли дополнять датасет своими съёмками, синтетикой или открытыми датасетами?
Да, это приветствуется.
B. Типы нарушений и вердикт
8. Есть ли закрытый список типов нарушений?
Нет. Перечень категорий из обучающего датасета также не раскрывается.
9. Могут ли в тесте встретиться типы нарушений, которых нет в обучающих данных?
Да.
10. Как отмечать нарушения «по бездействию», когда кассир не совершил обязательное действие? Какой таймкод указывать?
На усмотрение команды.
11. Какой вердикт ставить, если в одном видео найдено нарушение, а другой фрагмент неразборчив?
См. раздел «Обязательный пользовательский сценарий» в техническом задании.
C. Финальная проверка и баллы
12. Сколько видео будет на финальной проверке?
5+ видео.
13. Кто загружает видео на проверку?
Жюри — удалённо, по ссылке команды.
14. Есть ли лимит времени на обработку одного видео?
5 минут.
15. Критерий 1 считается по вердикту на всё видео или по каждому событию? Штрафуется ли злоупотребление вердиктом «Недостаточно данных»?
По вердикту на всё видео. Злоупотребление без обоснования штрафуется.
16. Что хуже для банка: ложное срабатывание или пропуск?
Ложных срабатываний должно быть как можно меньше, пропуск нарушения недопустим.
17. Какой допуск по таймкоду для критерия 2?
Нужно указать конкретный кадр и таймкод.
18. Оценка автоматическая или ручная?
Автоматическая. Результат выдаётся в JSON по единой схеме (см. раздел API в техническом задании).
19. Какой формат защиты?
Питчинг проводят только команды, прошедшие в финал (шортлист): 5 минут на выступление и 2 минуты на вопросы. Презентация — по желанию.
20. Как решается равенство баллов?
По результатам питчинга.
D. Технологии и инфраструктура
21. Можно ли использовать платные закрытые API (GPT, Gemini, Claude и т. п.)?
Нет. Решение должно работать локально.

24. Можно ли использовать заранее написанный код, шаблоны и предобученные модели?
Можно, если это open source с лицензией, разрешающей коммерческое использование.
25. Какой размер файла и какие форматы сервис обязан принимать?
.mov, около 29 МБ.

На выбор команды.
27. Нужны ли авторизация, история проверок, экспорт отчёта, пакетная загрузка?
Нет.
28. Можно ли использовать звук?
Нет, анализ строго визуальный.
29. Можно ли распознавать и идентифицировать лица?
Нет, это запрещено.
F. Нормативная база
30. Какая юрисдикция нормативных источников?
Только акты РК (НБРК, adilet.zan.kz).
31. Принимаются ли ссылки без точного пункта и открытые документы других банков?
Да.
32. Есть ли в датасете нарушения, основанные на внутренних правилах ForteBank, для которых нет открытого норматива?
Нет.
